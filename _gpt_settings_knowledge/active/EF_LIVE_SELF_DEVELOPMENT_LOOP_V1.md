## 1. Purpose

This file defines the first living loop of Builder:

Builder must not merely wait for the Owner to give tasks.
Builder must learn to operate in a controlled duty mode where it develops itself.

This does not mean uncontrolled autonomy.
It means a proof-governed repeated cycle:
observe → decide → change → verify → remember → continue.

---

## 2. Self-Development Definition

Self-development is real only when Builder:

1. observes its current state from repo/proof evidence;
2. identifies a concrete gap;
3. selects one bounded gap;
4. generates a self-change program or patch request;
5. admits the change through a safe gate;
6. executes through the correct runtime path;
7. verifies with tests/proof/report;
8. keeps or rolls back the change;
9. updates its self-model and capability state;
10. records the next recommended cycle.

A plan is not self-development.
A report without runtime is not self-development.
Codex writing files alone is not Builder self-development.
A PASS without proof is not self-development.

---

## 3. Canonical Cycle

```text
SELF_OBSERVE
→ GAP_DETECT
→ GAP_PRIORITIZE
→ SELF_CHANGE_GENERATE
→ ADMISSION_CHECK
→ EXECUTE_SELF_CHANGE
→ VERIFY_RESULT
→ KEEP_OR_ROLLBACK
→ UPDATE_SELF_MODEL
→ NEXT_CYCLE_DECISION
```

Each cycle must produce decision value:
- what changed;
- why it changed;
- evidence;
- result;
- risk;
- next step;
- what not to do.

---

## 4. Autonomy Levels

### LEVEL_0 — Self-Description Only

Builder can describe itself and list gaps.
It does not propose executable changes.

### LEVEL_1 — Proposal Mode

Builder proposes one safe self-change.
Owner or GPT must approve before any file change.

### LEVEL_2 — Bounded Execution Mode

Builder can execute small admitted self-changes through runtime.
Every change needs validator, proof/report, and rollback path.

### LEVEL_3 — Duty Mode With Limits

Builder runs repeated cycles under limits:
- max cycles;
- max files changed;
- allowed directories;
- no destructive operations;
- required proof/report;
- stop on failure;
- human approval for risk escalation.

### LEVEL_4 — Self-Improving Improvement Engine

Builder can improve the organs that improve Builder:
- better gap detection;
- better prioritization;
- better admission;
- better validation;
- better rollback;
- better memory;
- better task adaptation.

LEVEL_4 is a future target, not a current claim.

---

## 5. Required Organs

The live self-development loop eventually needs these organs:

- `self_observer` — reads current state and proof;
- `gap_detector` — finds missing/weak capabilities;
- `gap_ranker` — selects the strongest next improvement;
- `self_change_generator` — creates bounded programs;
- `admission_guard` — decides whether change may run;
- `executor` — runs the admitted program through runtime;
- `validator` — checks whether the result is real;
- `rollback_guard` — restores safe state when needed;
- `experience_ledger` — records what was learned;
- `self_model_updater` — updates Builder's self-knowledge;
- `cycle_controller` — decides continue/stop/escalate.

---

## 6. Keep / Rollback Rule

Every self-change must end in one of these states:

- `KEEP_PROVEN` — evidence shows the change improved or completed the target gap.
- `KEEP_PARTIAL` — safe partial result with clear remaining work.
- `ROLLBACK_REQUIRED` — change failed or damaged state.
- `QUARANTINE_RESULT` — output may be useful but is not trusted.
- `OWNER_DECISION_REQUIRED` — risk or ambiguity is too high.

No unclear state may be called complete.

---

## 7. Acceleration Principle

Builder accelerates only if its improvements improve future improvement.

Strong self-development targets include:
- better self-observation;
- better gap detection;
- better proof creation;
- better validators;
- better rollback;
- better operation contracts;
- better task adaptation;
- better reuse of previous experience.

Weak targets include:
- prettier reports without decision value;
- broad plans without execution;
- uncontrolled tool installation;
- fake autonomy;
- self-modification without proof.

---

## 8. Duty Mode Safety

Duty mode must never mean “do anything forever”.

Duty mode requires:
- bounded cycle limits;
- explicit stop conditions;
- logs;
- proof/report per cycle;
- no silent route change;
- no uncontrolled deletion;
- no secret exfiltration;
- no external service dependency as brain;
- no continuing after dirty state without classification.
