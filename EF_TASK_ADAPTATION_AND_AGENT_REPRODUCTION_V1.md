## 1. Purpose

This file defines how Builder should eventually handle external tasks.

The target is not:
```text
task arrives → GPT writes answer
```

The target is:
```text
task arrives
→ Builder detects what capability is missing
→ Builder grows the needed organ or child agent
→ task is executed
→ result is verified
→ useful experience returns to the main brain
```

Every task becomes evolutionary pressure.

---

## 2. Core Rule

Builder must not treat external agent production as simple file generation.

A produced agent must be a governed child form of Builder:
- created for a clear task or reusable class of tasks;
- bounded by contract;
- equipped with instructions;
- given input/output examples;
- runnable;
- validated;
- supported by proof/report;
- registered or indexed;
- able to return useful learning to Builder.

---

## 3. Task Adaptation Loop

```text
TASK_RECEIVE
→ TASK_UNDERSTAND
→ CAPABILITY_GAP_DETECT

→ ADMISSION_CHECK
→ BUILD_OR_GROW
→ RUN_TASK
→ VERIFY_RESULT
→ ABSORB_EXPERIENCE
→ UPDATE_MAIN_SELF_MODEL
```

This loop must not bypass the live self-development safety rules.

---

## 4. Organ vs Child Agent

### Organ

An organ is a reusable internal capability, for example:
- validator;
- parser;
- report writer;
- schema checker;
- material evaluator;
- operation wrapper;
- planner;
- task classifier.

### Child Agent

A child agent is a task-facing or domain-facing form, for example:
- math algorithm agent;
- repo audit agent;
- document builder agent;
- sales offer agent;
- validation agent;
- customer-specific workflow agent.

A child agent may later become an organ if its capability is useful for many tasks.

---

## 5. Absorption Rule

After a task is completed, Builder must not just discard the result.

It must decide what to absorb:

- new capability;
- new template;
- new validator;
- new material;
- new failure lesson;
- new test case;
- new task class;
- new agent pattern;
- new proof pattern;
- new risk rule.

Absorption must be explicit.
Do not silently merge untrusted outputs into the main brain.

---

## 6. Scaling Future

In the far future, Builder may receive many tasks at once.

Correct shape:

```text
main brain
→ task queue
→ task classification
→ grouping by capability class
→ child forms / worker organs
→ per-task proof
→ result verification
→ experience absorption
→ main self-model update
```

The main brain should not try to think about everything in one loop.
It should reproduce controlled specialist forms.

---

## 7. Million-Task Direction

The million-task idea is a strategic direction, not a current execution target.

Before large-scale task reproduction, Builder needs:
- reliable queue;
- task classifier;
- resource limits;
- sandbox;
- child-agent registry;
- per-task proof;
- failure isolation;
- memory compression;
- priority logic;
- security rules;
- cost/time budgets;
- parent-child experience protocol.

Do not jump to scale before single-task and small-batch proof.

---

## 8. Relationship To External Agents

External agents remain important, but their meaning changes.

Old weak meaning:
```text
create an agent folder and call it done
```

Correct meaning:
```text
Builder grows a task-specific child form,
runs it,
verifies it,
records proof,
and absorbs useful learning.
```

An agent is created only if:
- Builder executed the task path;
- folder exists;
- instructions exist;
- input/output example exists;
- runtime executed;
- proof/report exists;
- queue/state is safe;
- result can be seen or run.
